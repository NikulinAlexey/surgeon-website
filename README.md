# Сайт хирургического центра

Серверный монолит на Next.js с публичным сайтом, личным кабинетом, проверкой специалистов и административной панелью.

При неполадках используйте пошаговую инструкцию в [TROUBLESHOOTING.md](./TROUBLESHOOTING.md).

## Возможности

- регистрация, вход и серверные сессии в PostgreSQL;
- подтверждение email, повторная отправка письма и восстановление пароля;
- личный кабинет пациента и профиль специалиста;
- приватная загрузка документов и отдельное решение администратора о профессиональном статусе;
- статьи и новости с обложками, черновиками, отложенной публикацией и архивом;
- визуальный редактор, предпросмотр, история и восстановление версий;
- редактирование страниц, FAQ, контактов, SEO-полей, политики и соглашения;
- роли `PATIENT`, `SPECIALIST`, `EDITOR`, `ADMIN` и журнал административных действий;
- локальное хранилище на постоянном томе или S3-совместимое хранилище;
- редактируемые в админке сведения об организации, лицензии, врачах и медицинских услугах;
- публичные страницы лицензии, врачей, услуг, цен, доступности и отдельного согласия на обработку персональных данных;
- необязательная коммуникация, отзыв согласия, экспорт данных пользователя и удаление аккаунта с подтверждением пароля;
- skip-link «Перейти к содержимому» на публичных страницах и в админке.

## Требования

- Node.js 22.13 или новее;
- PostgreSQL 15 или новее;
- npm 10 или новее.

Не используйте Node.js 20: актуальные версии Prisma и sanitize-html требуют Node.js 22.

## Локальный запуск

1. Установите зависимости:

   ```sh
   npm ci
   ```

2. Создайте локальный файл настроек:

   ```sh
   cp .env.example .env
   ```

3. В `.env` замените пароли и укажите локальную базу, например:

   ```text
   DATABASE_URL=postgresql://surgeon:local-password@localhost:5432/surgeon
   APP_URL=http://localhost:3000
   ```

4. Создайте базу и примените миграции:

   ```sh
   npm run db:migrate
   npm run db:seed
   ```

   Seed создаёт первого администратора из `BOOTSTRAP_ADMIN_EMAIL` и `BOOTSTRAP_ADMIN_PASSWORD` только если в базе ещё нет администратора. Повторный запуск не перезаписывает редакторские изменения.

5. Запустите сайт:

   ```sh
   npm run dev
   ```

Сайт доступен на `http://localhost:3000`, административная панель — на `/admin`.

## Почта

В development без `SMTP_URL` письма сохраняются в `DEV_MAIL_DIR`. В production необходимо задать реальные `SMTP_URL` и `EMAIL_FROM`, иначе отправка подтверждений и восстановление пароля не будут работать.

Не помещайте SMTP-пароли, токены и содержимое писем в репозиторий или журнал.

## Загрузки и документы

Документы верификации не находятся в `public` и выдаются только через защищённый серверный маршрут администратора. Публичные обложки выдаются через отдельный маршрут медиа.

Для локального production-запуска задайте `LOCAL_STORAGE_DIR` на постоянном диске вне репозитория. Для S3 заполните `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID` и `S3_SECRET_ACCESS_KEY`. При полном S3-наборе локальное хранилище не используется.

## Docker Compose

Файл `docker-compose.yml` поднимает PostgreSQL, однократный контейнер миграций и standalone-приложение. Приложение запускается только после успешного `prisma migrate deploy` и seed.

1. Скопируйте `.env.example` в `.env` и задайте уникальные `POSTGRES_PASSWORD`, `BOOTSTRAP_ADMIN_PASSWORD`, `SMTP_URL` и публичный `APP_URL`.
2. Специальные символы в пароле базы должны быть URL-encoded, поскольку он входит в `DATABASE_URL`.
3. Запустите:

   ```sh
   docker compose up --build -d
   docker compose ps
   ```

PostgreSQL, загрузки и development-outbox используют отдельные named volumes. Health-check приложения обращается к `/api/health`, который дополнительно проверяет соединение с базой.

Остановка без удаления данных:

```sh
docker compose down
```

Не добавляйте `-v` к этой команде: флаг удаляет тома с базой и документами.

## Резервное копирование

Скрипт `scripts/backup.sh` создаёт дамп PostgreSQL в custom format, архив загрузок и SHA-256-контрольные суммы:

```sh
DATABASE_URL=postgresql://... \
LOCAL_STORAGE_DIR=/data/uploads \
BACKUP_DIR=/data/backups \
sh scripts/backup.sh
```

Скрипт должен выполняться на машине с `pg_dump` и доступом к базе. Храните резервные копии отдельно от основного сервера и регулярно проверяйте восстановление.

Восстановление выполняется только в пустую целевую базу. Скрипт не удаляет существующие таблицы и не перезаписывает непустой каталог загрузок:

```sh
RESTORE_DATABASE_URL=postgresql://... \
BACKUP_PATH=/data/backups/20261125T120000Z \
RESTORE_UPLOADS_DIR=/data/uploads \
sh scripts/restore.sh
```

Перед восстановлением остановите приложение. Создайте новую пустую базу заранее; не указывайте работающую production-базу.

## Проверки

```sh
npm run lint
npm run typecheck
npm test
npm run build
```

Браузерные тесты используют локальную тестовую базу и bootstrap-администратора из `.env`:

```sh
npx playwright install chromium
npm run test:e2e
```

Если Chromium уже установлен в системе, можно задать `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`. Не запускайте E2E против production: тест создаёт черновые материалы и события в журнале.
