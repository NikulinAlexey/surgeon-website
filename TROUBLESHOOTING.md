# Что делать при неполадках сайта

Инструкция для человека без доступа к нейросети. Выполняйте шаги по порядку и останавливайтесь после восстановления работы. Не применяйте сразу все команды подряд.

## 1. Сначала — безопасность

Нельзя без отдельной резервной копии и явной необходимости:

- удалять базу `surgeon`, PostgreSQL-тома или каталог `postgres-data`;
- удалять миграции из `prisma/migrations`;
- выполнять `docker compose down -v` — флаг `-v` удаляет тома с базой и документами;
- выполнять `git reset --hard`, `git clean -fd` или `git push --force`;
- обновлять все зависимости командой `npm update` в надежде, что это поможет;
- запускать E2E-тесты против production;
- публиковать `.env`, пароли, содержимое писем, токены, cookies или документы пользователей.

Безопасно:

- остановить и снова запустить приложение;
- перечитать логи и проверить порты;
- применить уже существующие миграции через `npm run db:migrate`;
- повторить `npm run db:seed`: он не создаёт второго администратора и не перезаписывает редакторские изменения;
- удалить только сборочный кеш `.next` после остановки сервера — он будет создан заново.

## 2. Зафиксируйте симптомы

Перед исправлением запишите:

1. Когда началась проблема и что менялось перед этим: код, `.env`, база, зависимости, сервер.
2. Точный адрес страницы и выполняемое действие.
3. Полный текст ошибки без сокращений.
4. Возникает ли ошибка в браузере, терминале, Docker, базе или GitHub Actions.

Команды ниже выполняются в Git Bash из корня проекта, если отдельно не указано PowerShell.

```sh
node -v
npm -v
git status --short --branch
curl http://localhost:3000/api/health
netstat -ano | grep -E ':(3000|5432)[[:space:]]'
```

Ожидаемые значения:

- Node.js `22.13.0` или новее, Node.js 20 не подходит;
- npm `10` или новее;
- health-check возвращает `{"status":"ok"}`;
- сайт слушает порт `3000`, локальная база — `5432`.

В Windows CMD вместо последней команды можно выполнить:

```bat
netstat -ano | findstr ":3000 :5432"
```

| `npm` или Prisma сообщает о несовместимости Node | Раздел 5 |

## 4. Сайт не запускается или процесс исчез

### 4.1. Запустите сервер вручную и оставьте терминал открытым

```sh
npm run dev
```

Проверьте:

```sh
curl http://localhost:3000/api/health
```

Если сервер запустился, не закрывайте этот терминал. Для остановки используйте `Ctrl+C`.

Если фоновый процесс исчез, а в конце лога нет ошибки, вероятнее всего он был остановлен извне, а не сломался код. Запустите его снова и запишите время остановки.

### 4.2. Порт 3000 уже занят

Next.js может автоматически перейти на порт `3001`. Тогда `localhost:3000` будет обслуживаться старым процессом, что выглядит как странные или устаревшие страницы.

Найдите PID:

```sh
netstat -ano | grep ':3000'
```

В PowerShell проверьте, что это именно Next.js текущего проекта:

```powershell
Get-CimInstance Win32_Process -Filter "ProcessId=<PID>" | Select-Object ProcessId,Name,CommandLine
```

Только если в `CommandLine` виден `start-server.js` этого проекта, остановите процесс:

```powershell
Stop-Process -Id <PID>
```

Не останавливайте все процессы `node.exe`: среди них могут быть другие приложения. После этого снова выполните `npm run dev` и проверьте порт 3000.

### 4.3. После `npm run build` dev-сервер ведёт себя странно

Остановите dev-сервер и его дочерний процесс Next.js, затем запустите заново:

```sh
npm run dev
```

Если проблема осталась, остановите сервер и очистите только сборочный кеш:

```sh
rm -rf .next
npm run dev
```

В PowerShell:

```powershell
Remove-Item -Recurse -Force .next
npm run dev
```

Не удаляйте `src`, `prisma`, базу или `node_modules` для очистки кеша Next.js.

## 5. Ошибки Node.js, npm и Prisma

Проверьте версии:

```sh
node -v
npm -v
```

Если используется nvm:

```sh
nvm install 22.13.0
nvm use 22.13.0
```

Затем переустановите зависимости строго по lockfile:

```sh
npm ci
```

`npm ci` также запускает `prisma generate`. При необходимости генерацию можно повторить отдельно:

```sh
npx prisma generate
```

Не заменяйте `npm ci` на обновление пакетов до новых версий. Сначала сохраните полный текст ошибки.

## 6. База данных и health-check

`/api/health` проверяет не только процесс Next.js, но и соединение с PostgreSQL. Если сайт открывается, а health-check падает, проверяйте базу.

### 6.1. Проверьте доступность PostgreSQL

Если установлены утилиты PostgreSQL:

```sh
pg_isready -h localhost -p 5432
psql -h localhost -p 5432 -U surgeon -d surgeon
```

Вторая команда запросит пароль пользователя базы. Не выводите `DATABASE_URL` и не отправляйте его в чат или журнал.

На текущей Windows-машине рабочая локальная база находится на `localhost:5432`. Другой PostgreSQL, принадлежащий KOMPAS-3D и работающий на порту `5433`, не используется сайтом и не должен останавливаться или изменяться.

Если рабочая база была создана отдельным кластером по локальной инструкции, её данные и лог находятся:

```text
C:/Users/Алексей/AppData/Local/surgeon-website/postgres-data
C:/Users/Алексей/AppData/Local/surgeon-website/postgres.log
```

Сначала прочитайте лог. Для повторного запуска этого кластера в Git Bash:

```sh
PGBIN="/c/Program Files/ASCON/KOMPAS-3D v23 Home/Libs/PolynomLib/Templates/LocalBase/bin"
PGDATA="C:/Users/Алексей/AppData/Local/surgeon-website/postgres-data"
PGLOG="C:/Users/Алексей/AppData/Local/surgeon-website/postgres.log"
"$PGBIN/pg_ctl.exe" -D "$PGDATA" -l "$PGLOG" -o "-p 5432" -w start
```

Если каталог или версия PostgreSQL на компьютере другая, не запускайте эту команду без корректировки путей.

### 6.2. Примените миграции

После успешного подключения к базе:

```sh
npm run db:migrate
npm run db:seed
```

`db:migrate` применяет существующие миграции, а `db:generate` создаёт новые. Для восстановления сайта не используйте `db:generate`.

### 6.3. Типовые причины ошибки базы

- PostgreSQL остановлен;
- база работает на другом порту;
- изменился пароль или пользователь;
- `DATABASE_URL` указывает не на локальную базу;
- не применена последняя миграция;
- закончилось место на диске.

Не пересоздавайте базу, пока не проверены эти пункты и не сделана резервная копия.

## 7. Ошибки HTTP и понятные сценарии

### `401 Unauthorized`

- Для входа проверьте email и пароль из локального bootstrap-настройщика.
- Для админки сессия могла истечь: войдите снова.
- Не делайте много попыток подряд — сработает ограничение частоты запросов.

### `403 Forbidden`

- У пользователя недостаточно прав. Для `/admin` нужны роли `EDITOR` или `ADMIN`.
- Не повышайте роль напрямую в production без разрешения ответственного администратора.

### `404 Not Found`

- Черновик недоступен публично — это ожидаемое поведение. Открывайте его через предпросмотр в админке.
- Если 404 у опубликованного материала, проверьте его статус, slug и дату публикации.
- Не меняйте маршруты API ради устранения ожидаемого 404.

### `429 Too Many Requests`

Для входа действует ограничение на 15 минут, для регистрации — на 60 минут. Подождите и попробуйте снова. Не создавайте дополнительных администраторов и не меняйте лимиты ради одного входа.

### Ошибка загрузки файла

Проверьте формат и размер: JPEG, PNG, WebP или PDF для документов, изображения для обложек, максимум 8 МБ на файл. Документы не должны переноситься в `public`.

## 8. Стили, иконки и изображения

1. Сделайте жёсткое обновление страницы: `Ctrl+F5`.
2. Проверьте ошибку в терминале Next.js и во вкладке браузера Network.
3. Пересоздайте SVG-спрайт:

   ```sh
   npm run sprite
   ```

4. Если проблема появилась после сборки, остановите сервер и очистите `.next` по разделу 4.3.

При полном исчезновении цветовых токенов проверьте `src/scss/main.scss` и `src/scss/global/_variables.scss`. Первое правило `:root` с резервной высотой шапки не является лишним: оно предотвращает проблему BOM, из-за которой dev-сборка Chrome могла не применить первый блок токенов. Не удаляйте его и `@charset "UTF-8"` без проверки в браузере.

Если не открывается загруженное изображение:

- проверьте запись в базе и ответ `/api/media/<id>`;
- проверьте доступность `LOCAL_STORAGE_DIR` или S3;
- не перемещайте приватные документы в `public`;
- убедитесь, что каталог загрузок существует и доступен процессу на запись.

## 9. Формы, сохранение и письма

Если кнопка сохранения неактивна:

- в личном кабинете сначала нажмите «Редактировать»;
- измените хотя бы одно поле — без изменений сохранение намеренно отключено;
- проверьте обязательные поля и ошибки рядом с ними;
- не путайте disabled-состояние с ошибкой API.

Если после сохранения появляется toast, данные считаются сохранёнными. Toast исчезает автоматически через несколько секунд — это не откат изменений.

В development при пустом `SMTP_URL` письма не отправляются через интернет, а сохраняются в `DEV_MAIL_DIR`. На текущей Windows-машине:

```text
C:/Users/Алексей/AppData/Local/Temp/surgeon-website-mail
```

Проверьте наличие JSON-файла письма и наличие каталога. Не прикладывайте к отчёту токен из письма.

В production пустой `SMTP_URL` является ошибкой конфигурации. Проверьте SMTP отдельно от базы и не публикуйте SMTP-пароль.

## 10. Docker Compose

Проверьте состояние контейнеров:

```sh
docker compose ps
docker compose logs --tail=200 app
docker compose logs --tail=200 db
docker compose logs --tail=200 migrate
```

`migrate` должен завершиться успешно; `app` запускается только после него. Для повторного запуска:

```sh
docker compose up --build -d
docker compose ps
curl http://localhost:3000/api/health
```

Для остановки без удаления данных:

```sh
docker compose down
```

Не добавляйте `-v`. Не удаляйте named volumes `postgres_data`, `uploads` и `mail` для устранения обычной ошибки запуска.

Если `docker` не найден, не устанавливайте его вместо существующего PostgreSQL без необходимости: для локального просмотра можно использовать отдельную базу напрямую.

## 11. Ошибки и предупреждения сборки

Выполните проверки и сохраните первую ошибку, а не только последние строки:

```sh
npm run lint
npm run typecheck
npm test
npm run build
```

На Windows Next.js может вывести предупреждение `EINVAL` при копировании standalone-файла с `node:buffer` в имени. Если сборка завершилась с кодом `0`, это не ошибка приложения. Для полноценной standalone-сборки используйте Linux/WSL или CI. Не удаляйте исходники и миграции из-за этого предупреждения.

Если `npm run build` завершился с ошибкой, dev-сервер после неё следует перезапустить, чтобы избежать смешанного кеша.

## 12. Git: потерянные изменения, push и повреждённые refs

Перед любыми действиями:

```sh
git status --short --branch
git diff
git diff --cached
git log -5 --oneline
```

Если есть нужные незакоммиченные изменения, сначала сохраните их отдельным коммитом или патчем. Не делайте `reset --hard`.

### Push отклонён как non-fast-forward

В удалённой ветке появились новые коммиты. Не используйте force-push. Сохраните текущую работу, затем получите изменения и разрешите конфликты:

```sh
git pull origin main
```

После проверки проекта выполните push повторно:

```sh
git push origin main
```

### `fatal: bad object refs/remotes/origin/main`

Это повреждение удалённой служебной ссылки, а не обязательно локальной ветки. Проверьте:

```sh
git show-ref --verify refs/remotes/origin/main
git fsck --no-dangling
```

Если ссылка содержит нули или повреждена, удалите только удалённые refs и их журналы, затем получите их заново:

```sh
rm -f .git/refs/remotes/origin/main .git/refs/remotes/origin/HEAD
rm -f .git/logs/refs/remotes/origin/main .git/logs/refs/remotes/origin/HEAD
git fetch origin main
git remote set-head origin -a
git pull origin main
git fsck --no-dangling
```

Локальная ветка `main` и файлы проекта этими командами не удаляются. При конфликтах pull остановитесь и разберите их вручную.

### Нужно отменить ошибочное изменение в репозитории

Используйте обратимый `git revert`, а не удаление истории:

```sh
git revert <HASH_КОММИТА>
npm run lint
npm run typecheck
npm test
npm run build
```

## 13. Резервная копия и восстановление

Создание резервной копии:

```sh
DATABASE_URL=postgresql://... \
LOCAL_STORAGE_DIR=/data/uploads \
BACKUP_DIR=/data/backups \
sh scripts/backup.sh
```

Храните копии отдельно от основного сервера и периодически проверяйте восстановление.

Восстановление выполняется только в новую пустую базу и после остановки приложения:

```sh
RESTORE_DATABASE_URL=postgresql://... \
BACKUP_PATH=/data/backups/<ДАТА_КОПИИ> \
RESTORE_UPLOADS_DIR=/data/uploads \
sh scripts/restore.sh
```

Не указывайте работающую production-базу. Скрипт не должен использоваться для очистки существующих таблиц.

## 14. Ошибка только в GitHub Actions

Откройте репозиторий:

```text
https://github.com/NikulinAlexey/surgeon-website/actions
```

Сравните ошибку с локальными командами из раздела 11. CI использует Node.js `22.13.0`, отдельную тестовую PostgreSQL и Chromium.

- Если локально всё проходит, сохраните полный лог упавшего шага CI.
- Если падает Playwright, проверьте установку Chromium и доступность тестовой базы.
- Не переносите production-пароли в CI и не запускайте E2E против production.

## 15. Когда нужна помощь другого разработчика

Подготовьте один пакет информации:

- точную команду или действие, вызвавшее ошибку;
- полный текст первой ошибки и стек;
- версии Node.js, npm и PostgreSQL;
- ответ `/api/health`;
- состояние портов 3000 и 5432;
- `git status --short --branch` и последние 5 коммитов;
- соответствующие логи Next.js, PostgreSQL или Docker;
- список последних изменений;
- скриншот, если проблема визуальная;
- что уже пробовали и какой был результат.

Не прикладывайте `.env`, пароли, токены, cookies, содержимое писем и пользовательские документы.

## 16. Быстрый контрольный список после восстановления

```sh
curl http://localhost:3000/api/health
npm run lint
npm run typecheck
npm test
```

Затем вручную проверьте:

- главную страницу;
- вход в `/admin`;
- список материалов;
- создание и предпросмотр черновика;
- редактирование профиля;
- страницу пользователей и заявок на верификацию.

Не запускайте production-проверки или E2E на боевых данных ради краткой проверки.
